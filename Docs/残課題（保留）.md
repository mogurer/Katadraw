## 2. ステージ管理の統一

今後、ステージ管理の責務とデータ経路を整理する必要がある。  
優先度は 1 から順に進める。

### 2.1 最終ステージ設定の生成を 1 本化する

#### 現状の課題
- ステージの有効設定を作る処理が複数ある。
- 同じ「欠損値を埋めてプレイ用設定を作る」処理なのに、未知 `type` の扱いなどが一致していなかった。

#### 目標
- 「このステージの最終的な設定は何か」を作る関数を 1 本化する。

#### 対応状況
- 対応済み。
- `StageConfig.build_effective_config()` を共通入口にし、`StageData` / `StageDebugOverrides` / `CustomStageFile` が同じ最終設定生成を通るよう整理した。

### 2.2 ステージ開始経路を統一する

#### 現状の課題
- 通常開始、デバッグテスト開始、ルール画面デモで初期化経路が異なる。
- `scripts/game.gd` から `StageManager.start_stage()` を使う経路と、`stage_manager` の一部フィールドを直接代入する経路が混在していた。

#### 目標
- すべてのステージ開始を共通の初期化 API に寄せる。

#### 対応状況
- 対応済み。
- `StageManager.start_stage_with_config()` と `game.gd` 側の開始 helper に寄せ、通常開始・デバッグテスト開始・ポーズからのやりなおし・ルール画面デモの入口を整理した。

### 2.3 ステージ関連の責務を `game.gd` から分離する

#### 現状の課題
- `scripts/game.gd` がステージ開始、デバッグ UI、pending 値、再開、カスタムステージ処理などを持ちすぎている。
- `StageManager` が「管理者」になりきっておらず、状態のオーケストレーションが分散している。

#### 目標
- ステージ関連の責務を `StageManager` または専用モジュールへ寄せる。

#### 対応状況
- 一部対応済み。
- `STAGE DEBUG` の状態管理を `StageDebugState`、結果集計と debug test 状態を `StageSession`、`STAGE EDIT` の状態を `StageEditState` に分離した。
- ただし、`STAGE EDIT` のキャンバス編集ロジック本体と、開始・再開・復帰の最終オーケストレーションはまだ `game.gd` 側に残っている。

### 2.4 `type` / `stage_id` / index の意味を整理する

#### 現状の課題
- 組み込みステージでは `type` が図形種別、カスタムステージでは ID 的な意味も混ざる。
- 本編ステージ index とデバッグ一覧 index が同一概念として扱われる箇所があり、再開やテスト時の不整合を招きやすい。

#### 目標
- 図形種別、ステージ識別子、表示順 index の役割を明確に分離する。

#### 対応状況
- 一部対応済み。
- ランタイム cfg に `shape_type` / `stage_id` / `stage_index` を持たせ、`StageManager.current_stage` は本編進行 index として扱うよう整理した。
- ただし、`STAGE DEBUG` の `type` 欄表示は built-in / custom で意味がまだ混在しており、仕上げは保留。

### 2.5 外部ステージデータの読込経路を統一する

#### 現状の課題
- `mbus` / `mug` は `CustomStageFile` 経由で読む一方、七芒星系は `scripts/stage_manager.gd` 内で直接 JSON を読んでいた。
- 同じ「外部 shape を持つステージ」でも、前提スキーマや読込責務が統一されていなかった。

#### 目標
- JSON 由来ステージの読込・検証・有効設定化を同一パイプラインに寄せる。

#### 対応状況
- 対応済み。
- `mbus` / `mug` に加えて `heptagram` / `heptagram_silhouette` も `StageData` の共通 helper + `CustomStageFile` 経由で row 化するよう統一した。
- `scripts/stage_manager.gd` から七芒星系の直接 JSON 読み込みは除去し、実行時は cfg に入った shape データを参照する形へ整理した。

#### 関連コード
- `Resources/stage_data.gd`
- `Resources/stage_config.gd`
- `scripts/stage_manager.gd`
- `scripts/stage_debug_overrides.gd`
- `scripts/custom_stage_file.gd`
- `scripts/game.gd`

## 3. 保守性・構造の改善

### 3.1 アーキテクチャ・責務分離

| 優先度 | 項目 | 内容 |
|--------|------|------|
| 中 | `game.gd` の最終分割 | ステージ開始・再開・復帰の最終オーケストレーションをさらに分離する |
| 中 | STAGE EDIT ロジック分離 | キャンバス編集ロジック本体を専用モジュールへ寄せる |
| 中 | シーン分離 | タイトル、メニュー、プレイ画面などを別シーン化し、シーン遷移で管理する |
| 中 | 定数・設定の外部化 | 色、レイアウト、タイミングなどの定数をさらにリソース化する |

### 3.2 コード品質

| 優先度 | 項目 | 内容 |
|--------|------|------|
| 中 | マジックナンバー | 座標、フォントサイズ、マージンなどが散在しているため定数化を進める |
| 中 | 重複コード | `rules` と `pause` の操作説明など、近い描画処理の共通化を検討する |
| 低 | 型アノテーション | 一部で型が省略されている箇所を補う |
| 低 | コメント整理 | 複雑な計算や意図が見えにくい箇所に説明を補う |

### 3.3 運用・ドキュメント

| 優先度 | 項目 | 内容 |
|--------|------|------|
| 中 | README | プロジェクト概要、起動方法、ビルド手順を整理する |
| 低 | ドキュメントの棚卸し | 調査メモと現行課題一覧の役割を重複させず維持する |

## 5. 解決済みの履歴

### 5.1 円ステージ「1点だけ伸ばす」問題【解決済み】

#### 現象
1点だけガイド円上に伸ばすと、他が崩れていても実現率が高くなる。

#### 試したこと
- **案F**: 誤差を「平均 + 最大」の複合スコアにする
  - `USE_COMBINED_ARC_ERROR := true`
  - `ARC_ERROR_AVG_WEIGHT := 0.7`、`ARC_ERROR_MAX_WEIGHT := 0.3`
- **結果**: 挙動はあまり変わらず。根が深そうな問題のため保留していたが、後続の評価整理で現行仕様へ着地。

### 5.2 ねこの顔ステージの評価【解決済み】

#### 現象
- 右耳・頭頂で実現率がズレる
- ポイントを外側へ動かすと実現率が上がる
- 打点分布によって実現率が変わる

#### 対応
- 輪郭ベース評価を維持しつつ、スケール基準を整理して現行仕様へ反映した。

## 6. ゲームプレイ体験の設計課題（保留中）

### 6.1 【優先検討】ガイド・頂点スナップの再設計

#### 背景
過去の整理作業で、以下の力をすべてリセットした。

- ポイントのガイドへの固定力
- ガイド頂点に対するポイントへの引力
- ガイド上のポイントの法線方向速度の削除（辺に張り付かせる処理）
- ポイントがガイド辺の内側に入り込まないよう押し返す力

**結果**として、現行仕様ではポイントがガイドや頂点にスナップする機能が存在しない。

#### 検討が必要な問い
- スナップを再実装するか？（どのような仕様で？）
- スナップを実装しないとすれば、「ハマっていく気持ちよさ」をどう実現するか？
- そもそもスナップなしでもゲームとして成立するか？

#### 判断が出るまで、後続の UX 改善（6.2）は保留とする

### 6.2 【保留】UX 改善候補（6.1 の方針決定後に着手）

以下はゲームプレイ体験の目標から導いた改善候補。6.1 の結論によって実装の可否・優先度が変わるため、現時点では保留。

#### 創りたい体験
- 各ポイントがガイド上や頂点にハマっていく気持ちよさ
- 思うように各ポイントを動かせない、もどかしさ
- ボタン2つだけで操作が完結する、簡単さ
- パッと見ただけでルールが理解できる、分かりやすさ

#### 体験させたくないこと
- ゲームルールに反した判定や動き
- ユーザーの自己責任ではない要因で発生する意図しない動き
- 操作に対してのラグや処理速度の低下

#### 改善候補一覧

**カテゴリ①：スナップの気持ちよさを強化する**

| 項目 | 内容 | 依存 |
|------|------|------|
| ①-A スナップ成功演出 | 頂点ロック成立時にポイントを一瞬フラッシュ（白・金）させる | 6.1でスナップを残す場合 |
| ①-B ポイントの状態別色分け | コーナーロック中=金、ガイド近傍=明るい色、遠い=現行色 | 6.1の方針次第 |
| ①-C 一致度の段階達成演出 | 80/90/95/98%通過時にスコア表示を強調する | 独立して実装可 |

**カテゴリ②：意図しない動きを根絶する**

| 項目 | 内容 | 依存 |
|------|------|------|
| ②-A 再接続の視覚通知（本番用） | デバッグ用赤ハイライトを製品向けの穏やかな演出に変換 | 独立して実装可 |
| ②-B プレイヤー操作中の再接続禁止 | `player_force_active == true` の間は再接続処理を停止 | 独立して実装可・効果大 |
| ②-C 静止状態の明示 | 全ポイントが速度ゼロに収束したとき、微かなアニメで「落ち着いた」を伝える | 独立して実装可 |

**カテゴリ③：2ボタン操作の分かりやすさを高める**

| 項目 | 内容 | 依存 |
|------|------|------|
| ③-A 引力・斥力フィールドの常時薄表示 | 操作中だけでなく常に薄く表示し、切り替わりを明示 | 独立して実装可 |
| ③-B 最近接コーナーのハイライト | プレイヤー近くのガイドコーナーを薄く強調表示 | 6.1でスナップを残す場合に特に有効 |

**カテゴリ④：ゲームルールの可視化**

| 項目 | 内容 | 依存 |
|------|------|------|
| ④-A ガイドとの対応線（オプション） | 各ポイントから最近接ガイド点への薄い線（ヒントとして切り替え式） | 独立して実装可 |
| ④-B スコア貢献のゾーン表示 | スコアに悪影響のポイントを赤みがかった色で表示 | 独立して実装可 |
